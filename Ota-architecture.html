Autonomous Fleet OTA Intelligence

ML-powered OTA campaign intelligence for autonomous vehicle fleets. Eligibility gating, XGBoost risk scoring, staged rollout with auto-promote/pause/stop, 7-ECU dependency orchestration with topological ordering, dependency-aware cascade rollback, and A/B cohort comparison. Nine real-world failure modes handled end-to-end.

UPTANE MQTT XGBoost SHAP NetworkX FastAPI PostgreSQL
01 /

The Problem

An autonomous fleet of 5,000 vehicles, each with 7 ECUs running different firmware versions on different hardware revisions. A single bad OTA push can brick hundreds of vehicles overnight. Perception AI crashes on boot, brakes ECU won't respond, gateway firmware corrupted mid-flash. This actually happens.

You can't just push firmware to everyone. Vehicle A has 20% battery and will die mid-flash. Vehicle B is driving on a highway. Vehicle C has old hardware with a 23% historical failure rate. Vehicle D has a source version mismatch for delta updates. Vehicle E is in rural Montana on cellular only, too slow for a full image download. You need intelligence between "firmware is ready" and "firmware is installed."

Eligibility Engine
7 pre-conditions checked per vehicle before any update attempt
▸

Every vehicle must pass all seven checks before it's allowed into the update pipeline. A single failure blocks the vehicle with a logged reason. This is the first and cheapest line of defence: you don't waste risk scoring compute on a vehicle that's driving on a highway or has 15% battery.

1. Vehicle State
Must be parked with ignition off (gear in P)
2. Battery SOC
> 60% for gateway/perception, > 40% for infotainment
3. Connectivity
WiFi required for full images, cellular OK for delta only
4. Diagnostics
No active diagnostic session (UDS 0x10 non-default)
5. FW Compatibility
Current version must be in the update's source version list
6. HW Revision
Target firmware must support this hardware revision
7. Campaign Window
Must be within the campaign's scheduled rollout window
Output
Eligible / Blocked + specific reason code for audit log

Risk Scoring Engine (XGBoost)
12-feature ML model predicts per-vehicle update failure probability
▸

For each eligible vehicle, an XGBoost classifier predicts the probability of update failure. The model is trained on historical update outcomes across the fleet. SHAP values explain every prediction: "High risk because HW Rev 1 has a 23% historical fail rate, delta update with uncertain version history, and declining battery SOC trend."

Feature 1-3
Historical failure rate per ECU HW revision, connectivity stability, battery SOC trend
Feature 4-6
Delta vs full image, versions behind count, geographic region
Feature 7-9
Time since last successful update, concurrent ECU count, vehicle age
Feature 10-12
Ambient temperature, previous rollback count, flash partition health
Output
Risk score 0-100 + SHAP feature importance per prediction
Model Tracking
MLflow experiment tracking, versioned models, metrics history

Staged Rollout
1% canary → 10% → 50% → 100% with auto-promote/pause/stop
▸

Eligible vehicles are sorted by risk score (lowest risk first) and deployed in four stages. Each stage runs for a configurable hold period, during which the monitor watches failure rate. Promotion, pause, and stop decisions are automatic based on observed failure rate thresholds.

Stage 1: Canary
Lowest-risk 1% of fleet. Prove the update works on real hardware.
1% of fleet · 48hr hold
failure rate < 2%? promote ↓
Stage 2: Early Adopters
Next 10% of fleet by risk score. Broader hardware coverage.
10% of fleet · 24hr hold
failure rate < 2%? promote ↓
Stage 3: Majority
50% of fleet. Stress tests infrastructure at scale.
50% of fleet · 24hr hold
failure rate < 2%? promote ↓
Stage 4: Full Fleet
Remaining vehicles including higher-risk profiles.
100% of fleet
Auto-decision thresholds: Failure rate < 2% → auto-promote to next stage. Failure rate 2-5% → PAUSE, alert engineering for investigation. Failure rate > 5% → STOP campaign, trigger rollback for affected vehicles.

Rollback Engine

When an ECU flash fails mid-sequence, the rollback engine must decide: can the vehicle safely run with a mix of old and new firmware, or does every previously-updated ECU need to go back too? This is not a simple undo. It's a dependency-aware cascade decision backed by a compatibility matrix and an ML-predicted rollback success probability.

⚠
Cascade Rollback Logic
Compatibility check → single or cascade rollback → ML success prediction
▸

Example scenario: Gateway updated successfully to v3.0, Perception updated to v2.1, Planning fails at 67%. The rollback engine checks the compatibility matrix: can Gateway(v3.0) + Perception(v2.1) + Planning(v_old) coexist? If yes, only Planning rolls back. If no, all three must cascade back to their previous versions.

Cascade Rollback Path

1. Planning fails at 67% → rollback Planning to v_old.
2. Check compatibility: Gateway(new) + Perception(new) + Planning(old) → INCOMPATIBLE.
3. Cascade: roll back Perception to v_old, then Gateway to v_old.
4. Reverse topological order: Planning → Perception → Gateway.
5. Before each rollback, ML model predicts success probability.

ML Rollback Prediction

Before executing each rollback step, a second XGBoost model predicts rollback success probability. "Planning rollback: 91% predicted success." "Perception rollback: 78%, call a technician." This enables the fleet manager to decide whether to attempt automated rollback or dispatch field service.

Compatibility Matrix
Per-ECU version pair compatibility table, checked before every rollback
Rollback Order
Reverse topological sort of the dependency graph
Success Prediction
XGBoost per-step success probability with SHAP explanation
Fallback
If ML predicts < 70% success, flag for manual field service

Nine Failure Modes

Every failure mode that can occur in a real fleet OTA deployment is simulated and handled. The system doesn't just detect these failures, it has a defined recovery path for each one.

# Failure Mode Detection Recovery Severity
F1 Download timeout No progress for 120s Retry with exponential backoff, switch to full image if delta Medium
F2 Package corruption SHA-256 hash mismatch Re-download from UPTANE Image Repository, full integrity check High
F3 Flash write failure Flash controller error code Rollback to previous partition (A/B scheme), log DTC Critical
F4 Boot failure after flash ECU fails self-test within 30s Boot from backup partition, cascade rollback check Critical
F5 Self-test failure Diagnostic routine 0x31 returns NOK Rollback + flag for service, set DTC Critical
F6 Dependency conflict Compatibility matrix mismatch post-flash Cascade rollback of dependent ECUs in reverse topological order Critical
F7 Battery died mid-flash Voltage drop below threshold Resume from last checkpoint on next power cycle, verify partition Critical
F8 Verification failure UPTANE metadata signature invalid Reject update, report to Director Repository, block retry High
F9 Vehicle drove away mid-flash Ignition state change to RUN Pause flash, resume on next park cycle, verify partial state High

📈
A/B Cohort Comparison
Statistical validation that the update improved outcomes
▸

After rollout completes, the system compares the updated cohort against the control cohort (vehicles that haven't updated yet) using t-test and Mann-Whitney U tests. This produces a statistically validated report: "Boot time improved 12% (p < 0.01), sensor health: no regression, error rate: -8%." Auto-generated for engineering review.

Independent t-test, Mann-Whitney U (non-parametric)
Metrics Compared

p-value threshold < 0.05 with confidence intervals

Key Design Decisions

?
Why ML risk scoring and not just rules?
Feature interactions, fleet-level learning, continuous improvement
▸

A rule-based system can check "is battery above 60%?" but it can't learn that HW Rev 1 devices with declining battery SOC on cellular connections have a 4x higher failure rate than the same hardware on WiFi. XGBoost captures these feature interactions automatically from historical data. As the fleet grows and more updates are deployed, the model improves. SHAP explainability means every prediction is transparent and auditable, not a black box.

?
Why UPTANE and not a custom signing scheme?
Automotive industry standard, attack-resistant design
▸

UPTANE is the automotive industry's purpose-built OTA security framework. Its dual-repo architecture (Image Repository + Director Repository) with role-based key hierarchy protects against rollback attacks, freeze attacks, and mix-and-match attacks. A custom signing scheme would need to solve all of these attack vectors from scratch. UPTANE has been formally analysed and is adopted by major OEMs. For regulatory compliance and cybersecurity audits, using an established framework is non-negotiable.

?
Why dependency-aware rollback and not full fleet rollback?
Minimise blast radius, preserve successful updates
▸

A naive "rollback everything" approach wastes completed work and extends fleet downtime. If Gateway and Perception updated successfully and only Planning failed, and the compatibility matrix confirms Gateway(new) + Perception(new) + Planning(old) is safe, there's no reason to touch Gateway and Perception. The dependency-aware approach only rolls back what's necessary. When it does need to cascade, it follows the reverse of the topological sort order to maintain consistency at every step.

?
Why A/B cohort testing for firmware?
Evidence-based validation, not assumption-based deployment
▸

In web software, A/B testing is standard. In automotive OTA, most companies just push and hope. The staged rollout naturally creates a control cohort (the vehicles that haven't updated yet). Comparing updated vs control vehicles with statistical tests produces objective evidence that the update improved performance. This is critical for regulatory audits and for building engineering confidence in the OTA pipeline.
