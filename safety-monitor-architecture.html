AD Real-Time Safety Monitor

ISO 26262 ASIL D fault management system on ROS2. Five sensor health monitors, cross-sensor correlation engine, degradation state machine with hysteresis, UDS/DoIP diagnostic server, and MQTT fleet telemetry. Validated across six fault injection scenarios with measured detection latency and false-positive rates.

ROS2 ISO 26262 UDS / DoIP SOME/IP MQTT nuScenes

System Overview

The safety monitor sits alongside the autonomous driving stack, not inside it. It is an independent supervisor that watches sensor health, detects faults, correlates failures across modalities, and commands vehicle-level degradation responses. It does not trust the AD stack's self-reported health. Every fault detection has a measured latency budget, every state transition has hysteresis to prevent oscillation, and every response maps to an ISO 26262 ASIL-rated safety requirement.

The system is built on ROS2 Humble using lifecycle-managed nodes. Data flows through a four-stage pipeline: sensor monitoring, fault detection, cross-sensor correlation, and safety response. A UDS diagnostic server over DoIP exposes AD-specific DTCs to off-board tools, and MQTT uplinks fleet-level telemetry for remote monitoring.

Architecture Layers

📡
Sensor Health Monitors
Five independent monitors at 10 Hz — camera, LiDAR, radar, compute, network
▸

Each sensor modality has a dedicated ROS2 lifecycle node running at 10 Hz. The monitors don't process perception data. They track health signals: frame rates, point cloud density, noise floors, processing latency, and packet integrity. Each publishes a normalised health score (0 to 100) to a shared diagnostics topic.

Camera Monitor
Frame rate, blur (Laplacian variance), exposure, dropped frames
LiDAR Monitor
Point density, calibration drift, range consistency, stale timestamps
Radar Monitor
Noise floor, false target rate, range accuracy, update frequency
Compute Monitor
Inference latency, GPU utilisation, memory pressure, thermal throttling
Network Monitor
Packet loss, sequence gaps, CAN bus load, Ethernet link status
Update Rate
10 Hz per monitor — 50 health checks per second total
⚡
Fault Detection
Three detection mechanisms — watchdogs, thresholds, rolling z-score anomaly
▸

Fault detection runs three mechanisms in parallel. Heartbeat watchdogs catch complete sensor failures (no data arriving). Threshold monitors catch out-of-range values (point density below minimum, latency above budget). Rolling z-score anomaly detection catches gradual degradation that hasn't yet crossed a hard threshold. All three feed into the per-sensor health score.

Heartbeat Watchdog
Detects sensor liveness failure within 100ms timeout
Threshold Monitor
Configurable per-sensor bounds, immediate fault on breach
Z-Score Anomaly
Rolling 30s window, flags gradual drift before hard failure
Latency Budget
< 5ms end-to-end detection — must not slow perception pipeline
🔗
Cross-Sensor Correlation Engine
Voting logic, temporal alignment, shared root cause detection
▸

A single sensor fault alone does not trigger vehicle degradation. The correlation engine cross-checks faults across modalities and assigns a confidence score. If LiDAR reports degradation but camera and radar are nominal, that's a different response than if two sensors degrade together. This is the key differentiator from simple threshold-based monitoring.

The engine uses voting logic (majority of sensors must agree on degradation) and temporal correlation (faults must persist for a configurable window before escalation). It also detects shared root causes: if camera and LiDAR both degrade simultaneously, it checks whether a common factor (rain, mud on sensor housing, compute overload) explains both, rather than treating them as independent failures.

Voting Quorum
2 of 3 primary sensors must confirm before degradation
Temporal Window
500ms sustained fault required for state transition
Root Cause Analysis
Co-temporal failures checked against shared cause table
Output
Composite system health score (0-100) with per-sensor breakdown
🛡
Safety Response Engine
ISO 26262 ASIL D state machine with hysteresis — four degradation levels
▸

The state machine maps composite health scores to four ISO 26262-aligned degradation levels. Transitions require sustained score thresholds (hysteresis) to prevent oscillation at state boundaries. Each state has a defined vehicle response, DTC code, and recovery path.

Nominal
Full autonomous operation. All systems healthy.
Score 80 – 100
score < 80 for 500ms ↓
Reduced ODD
Lower max speed, increase following distance, avoid complex intersections.
Score 60 – 79 · DTC: U0501
score < 60 for 200ms ↓
Minimal Risk Condition
Initiate controlled pullover to safe location. Request driver takeover (L3).
Score 30 – 59 · DTC: U0502
score < 30 for 100ms ↓
Immediate Safe Stop
Maximum deceleration, hazard lights, notify fleet operations.
Score 0 – 29 · DTC: U0503
Hysteresis logic: Downward transitions (degrade) require the score to stay below threshold for 500ms. Upward transitions (recovery) require the score to stay above threshold for 2000ms. This asymmetry is intentional: entering a safer state should be quick, recovering to a less safe state should be slow and confirmed. This prevents rapid oscillation at state boundaries from sensor noise.
Recovery Path

The system doesn't just fail forward. When sensor health improves and the composite score rises above the recovery threshold for 2 seconds, the state machine transitions back toward nominal. Recovery is validated: the system confirms sustained health improvement before restoring higher-autonomy modes.

UDS/DoIP Diagnostic Server
AD-specific DTCs, freeze frames, standard off-board diagnostic access
▸

A UDS diagnostic server implemented with python-udsoncan over DoIP transport exposes AD-specific diagnostic trouble codes through standard automotive protocols. Off-board diagnostic tools connect via DoIP (ISO 13400) and read DTCs, freeze frames, and live health data using standard UDS services (0x19, 0x22, 0x14).

DTC Codes
U0501 (perception degraded), U0502 (MRC active), U0503 (safe stop)
Freeze Frames
Full system state snapshot at moment of fault trigger
Live Data
Per-sensor health scores, composite score, current state via 0x22
Transport
DoIP (ISO 13400) over TCP — remote diagnostic access
☁
MQTT Fleet Telemetry Uplink
Real-time health telemetry to cloud fleet backend
▸

Health telemetry is published over MQTT (TLS 1.3) to a cloud fleet backend. This enables remote monitoring of fleet-wide sensor health, trending analysis for predictive maintenance, and operational decisions about when to pull a vehicle for service. QoS 1 ensures delivery of state-change events.

Protocol
MQTT 5.0 over TLS 1.3, QoS 1 for state changes
Payload
JSON — per-sensor scores, composite score, current state, DTCs
Frequency
1 Hz nominal, immediate on state transition
Fleet Dashboard
Aggregated health view, anomaly trending, service scheduling

FMEA and ASIL Decomposition

Each fault mode carries an ASIL rating derived from hazard analysis. Single-sensor failures are lower severity (the remaining sensors provide redundant coverage). Multi-sensor failures or compute failures that affect the entire perception pipeline carry ASIL D, the highest integrity level.

Fault Mode Detection Method Detection Time Response ASIL
Camera image loss Frame rate monitor < 100ms Reduce ODD, rely on LiDAR + radar ASIL B
Camera blur / occlusion Laplacian variance < 200ms Reduce speed, flag maintenance ASIL B
LiDAR point density drop Density vs threshold < 100ms Reduce ODD, rely on camera + radar ASIL B
LiDAR total loss Stale timestamp < 100ms MRC — initiate pullover ASIL B
Camera + LiDAR loss Cross-sensor correlation < 100ms Immediate safe stop ASIL D
Radar ghost targets False detection spike < 500ms Increase following distance ASIL A
Compute latency spike Processing time monitor < 200ms Reduce speed ASIL C
Compute failure Heartbeat + watchdog < 100ms Immediate safe stop ASIL D
ROS2 node crash Lifecycle state monitor < 500ms MRC if critical node ASIL C
Network packet loss Sequence gap detection < 200ms Reduce speed, flag maintenance ASIL C

Fault Injection Scenarios

Six degradation scenarios validated end-to-end using ROS2 bag files with injected faults. Source data from nuScenes dataset with offline degradation injection. Each scenario measures detection latency, false-positive rate, and state machine response time.

S1
LiDAR Point Cloud Dropout
Progressive reduction of point density from 100% to 20% over 10 seconds, simulating sensor degradation from dirt accumulation or partial hardware failure. Expected transition: Nominal → Reduced ODD at 60% density.
Detection: < 80ms
FP Rate: < 2%
S2
Camera Frame Freeze
Camera output stops updating (frozen frame). Watchdog detects stale timestamps. Expected transition: Nominal → Reduced ODD → MRC if sustained beyond 2 seconds.
Detection: < 100ms
FP Rate: < 1%
S3
IMU Drift Injection
Gradual bias drift injected into accelerometer readings. Z-score anomaly detection catches drift before it crosses hard thresholds. Tests the rolling health score mechanism.
Detection: < 500ms
FP Rate: < 3%
S4
Simultaneous Multi-Sensor Failure
Camera and LiDAR fail simultaneously. Cross-sensor correlation confirms multi-modal failure. Expected transition: Nominal → Immediate Safe Stop (bypasses intermediate states). This is the ASIL D scenario.
Detection: < 100ms
FP Rate: 0%
S5
CAN Bus Noise Injection
Elevated error frames and bus load on the CAN network. Network monitor detects degraded communication quality. Tests the network health scoring pathway independently.
Detection: < 200ms
FP Rate: < 2%
S6
Transient Glitch with Recovery
Brief sensor dropout (300ms) followed by full recovery. Tests that the hysteresis logic correctly prevents state oscillation and that the recovery path works as designed. Expected: brief dip in health score, no state transition due to hysteresis.
Detection: < 100ms
Transition: None (correct)

Key Design Decisions

?
Why ROS2 and not a custom middleware?
DDS transport, lifecycle management, ecosystem
▸

ROS2 provides DDS-based communication with configurable QoS profiles, which gives deterministic messaging without building a custom transport layer. Lifecycle-managed nodes map directly to the ECU boot sequencing concept from AUTOSAR: each monitor node transitions through unconfigured → inactive → active → finalized, which gives the safety response engine explicit control over system startup and shutdown ordering. The alternative was building a custom pub-sub framework on SOME/IP, but that duplicates infrastructure ROS2 already provides and reduces portability across AD platforms.

?
Why cross-sensor correlation and not per-sensor thresholds?
False positive reduction, shared root cause detection
▸

Per-sensor thresholds generate too many false positives. A LiDAR density dip during heavy rain is expected if camera also shows degradation. Treating them independently would trigger two separate fault responses. The correlation engine recognises this as a single environmental cause and responds proportionally. Without correlation, a rain event could cascade through multiple monitors and trigger a safe stop that isn't warranted by actual risk.

?
Why asymmetric hysteresis?
Fast degradation, slow recovery
▸

The degrade path uses short hysteresis (100-500ms) because entering a safer state quickly is always the right default. The recovery path uses long hysteresis (2000ms) because returning to a less-safe state should require sustained evidence of improvement. This asymmetry prevents a flickering sensor from bouncing the state machine between nominal and degraded on every cycle. In production, this is the difference between a smooth ride with occasional reduced capability and a vehicle that constantly jerks between speed profiles.

?
Why UDS/DoIP for diagnostics?
Standard tooling, regulatory compliance, fleet integration
▸

UDS (ISO 14229) over DoIP (ISO 13400) means every existing off-board diagnostic tool in any OEM or Tier 1 shop can connect and read AD-specific DTCs without custom software. This is not optional for production vehicles: regulatory diagnostics require standard protocol access. The alternative (proprietary API) would work for development but fails in production service environments where technicians use standard scan tools. DoIP specifically enables remote diagnostics over Ethernet, which is critical for fleet-managed autonomous vehicles.
