Architecture

  • 100s of standalone ECUs, each with dedicated MCU + memory
  • Direct peer-to-peer wiring — no central compute
  • ~1 ECU per feature: windows, wipers, HVAC each separate
  • Wire harness: 40–80 kg in luxury vehicles
AUTOSAR Classic only

Protocols

  • CAN (2 Mbps max) as primary backbone
  • LIN for low-bandwidth peripherals (switches, sensors)
  • K-Line / ISO 9141 for diagnostics
  • FlexRay for safety-critical chassis in some OEMs
  • ISO 14229 (UDS) over CAN for diagnostics

Challenges driving change

  • Software updates require physical dealer visit
  • Feature additions require new ECU hardware
  • No software reuse across ECUs or OEM platforms
  • Diagnostic coverage limited by CAN bandwidth
  • Integration test complexity grows exponentially

Architecture

  • ECUs grouped into domains: Powertrain, Body, Chassis, ADAS, IVI
  • Domain Controller (DCU) acts as gateway + compute hub per domain
  • Cross-domain comms via central gateway ECU
  • Backbone Ethernet begins replacing interior CAN
AUTOSAR Classic + early Adaptive

Protocols

  • CAN FD (8 Mbps) replaces CAN in new designs
  • 100BASE-T1 Automotive Ethernet for domain backbones
  • SOME/IP for service-oriented inter-domain communication
  • DoIP (ISO 13400) enables diagnostics over Ethernet
  • OBD-II still mandated for regulatory compliance

What changes

  • Middleware layer introduced — AUTOSAR BSW, SOME/IP
  • Gateway ECU becomes software-defined — my NIO work
  • OTA updates possible at domain level
  • Security perimeter now meaningful (Ethernet attack surface)
  • Reduced ECU count, higher per-ECU complexity

Architecture

  • ECUs grouped by zone (Front-Left, Front-Right, Rear) not function
  • Zone Controllers aggregate local sensor/actuator nodes
  • Backbone Ethernet connects zones to central compute
  • Tesla Model 3, VW E3, Volvo SPA2 examples
AUTOSAR Adaptive on zone controllers

Protocols

  • 1000BASE-T1 Gigabit Automotive Ethernet backbone
  • CAN FD retained at leaf nodes (sensors/actuators)
  • SOME/IP over Ethernet for inter-zone services
  • DoIP over Ethernet — single diagnostic entry point
  • MQTT or DDS for telemetry uplink to cloud

What changes

  • Software abstraction: zone controller hides topology from apps
  • OTA targets zone controller + all sub-nodes in one campaign
  • Diagnostic entry centralized — single VIN-level access
  • Cybersecurity: Ethernet firewall rules per zone, IDS needed
  • AUTOSAR Adaptive enables POSIX OS, dynamic services

Architecture

  • 1–3 high-compute Vehicle Computers replace domain controllers
  • Hardware-software decoupling: apps run as containers/VMs
  • Vehicle Abstraction Layer hides ECU topology from apps
  • Continuous deployment: vehicle as a software platform
  • Rivian R2, Zeekr, NIO ET9 early SDV examples
AUTOSAR Adaptive · Linux · ARA

Protocols

  • Multi-Gb Ethernet backbone (2.5G / 10G)
  • DDS or SOME/IP for internal service mesh
  • MQTT / HTTPS for cloud uplink (UPTANE for OTA security)
  • UDS/DoIP remains for regulatory diagnostics
  • CAN FD lives on as leaf protocol near actuators
  • V2X (DSRC / C-V2X) for infrastructure comms

What changes

  • Features monetized post-sale: OTA enables subscription model
  • CI/CD pipelines extend to vehicle — fleet as deployment target
  • ML inference moves on-vehicle (ADAS, health monitoring)
  • Diagnostic intelligence shifts from read codes to predictive AI
  • Safety: ISO 26262 must account for OTA-updated software
  • Security: zero-trust, secure boot, signed OTA packages

Protocol Mapping by Layer

◈ Hover any protocol badge for a technical summary. Protocols are shown at their primary operating layer — some (like UDS) span multiple layers via transport adaptation.
Cloud
Internet / V2C
MQTT 5.0
Publish-subscribe over TCP. QoS 0/1/2. Used for vehicle telemetry uplink to cloud fleet backends. Mosquitto broker common in automotive. Lightweight enough for always-on 4G vehicle connections.
 HTTPS / REST
Standard web transport for OTA manifest fetch, campaign management APIs, and fleet dashboards. TLS 1.3 mandatory in modern vehicle cloud architectures.
 UPTANE
Automotive OTA security framework. Dual-repo (Image + Director). Role-based key hierarchy (Root, Targets, Snapshot, Timestamp). Protects against rollback, freeze, and mix-and-match attacks. My P3 implements full UPTANE.
 DDS / ARA::COM
Data Distribution Service. Pub/sub with QoS policies. Used in AUTOSAR Adaptive ARA::COM for inter-process communication. Alternative to SOME/IP in some SDV platforms and in ROS2 (DDS backend).
Diagnostics
Off-board / OBD
DoIP (ISO 13400)
Diagnostics over Internet Protocol. Routes UDS messages over TCP/UDP + Ethernet. Replaces K-Line and CAN-based diagnostic transport. Enables remote diagnostics. My P2 and P4 both implement DoIP servers via python-udsoncan.
 UDS (ISO 14229)
Unified Diagnostic Services. Application-layer protocol for ECU diagnostics. Services: 0x10 (session), 0x19 (read DTC), 0x22 (read data), 0x2E (write), 0x31 (routine), 0x34–0x36 (flash). Runs over CAN, DoIP, or SOME/IP.
 OBD-II / ISO 15765
Regulatory on-board diagnostics. Mandated since 1996 (US) / 2003 (EU). Mode $01–$0A for emissions, freeze frame, DTC read. CAN-based transport (ISO 15765-4). Cannot be replaced by proprietary protocols for emissions compliance.
Middleware
Service layer
SOME/IP
Scalable service-Oriented MiddlewarE over IP. Service discovery (SOME/IP-SD), remote procedure calls, events, and fields over UDP/TCP + Ethernet. Core middleware for AUTOSAR Adaptive and domain-based architectures. My P1 IDS covers SOME/IP traffic.
 AUTOSAR Classic BSW
Basic Software in AUTOSAR Classic. COM stack, DCM (diagnostic comm manager), NM (network management), PDU Router. Runs on bare-metal RTOS. Used in body ECUs, powertrain ECUs, gateway modules.
 AUTOSAR Adaptive ARA
AUTOSAR Runtime for Adaptive Applications. POSIX-compliant OS. ara::com (SOA comms), ara::diag (diagnostics), ara::exec (execution mgmt), ara::crypto, ara::ucm (OTA). Used on domain/zone controllers and Vehicle Computers.
 Vehicle Abstraction Layer
Software layer hiding ECU topology from application services. Apps subscribe to signals ("vehicle.speed_kmh") without knowing which physical ECU generates them. Key SDV enabler. Open implementations: Eclipse Kuksa.VAL, COVESA VSS.
In-Vehicle Ethernet
Domain / Zonal backbone
100BASE-T1
100 Mbps single-pair automotive Ethernet (IEEE 802.3bw). Unshielded twisted pair, BroadR-Reach PHY. Domain backbone in current-gen vehicles. Suited for camera streams, gateway uplinks. BMW, Audi, VW Group adoption.
 1000BASE-T1
Gigabit single-pair automotive Ethernet (IEEE 802.3bp). Zonal backbone in next-gen architectures. Connects zone controllers to central compute. Required for streaming LiDAR point clouds and multi-camera data.
 AVB / TSN
Audio Video Bridging / Time-Sensitive Networking. IEEE 802.1AS (timing sync), 802.1Qbv (traffic scheduling), 802.1CB (frame replication). Deterministic latency over Ethernet — critical for ADAS sensor fusion and chassis control loops.
In-Vehicle Bus
ECU interconnect
CAN FD (ISO 11898)
CAN with Flexible Data-rate. Up to 8 Mbps data phase, 64-byte payload vs CAN's 8 bytes. Backward compatible with CAN 2.0. Standard for new ECU designs. Still dominant at sensor/actuator level in zonal architectures. My P1 IDS analyzes CAN FD traffic.
 CAN 2.0 (Classic)
Controller Area Network. 1 Mbps, 8-byte frames, CSMA/CD arbitration. Ubiquitous since 1994. Still in body control, powertrain, instrument clusters. Priority-based bus arbitration via 11/29-bit identifier.
 LIN 2.x
Local Interconnect Network. Single-wire, 20 kbps, master-slave. Low-cost, low-bandwidth peripheral bus. Seat motors, mirror adjustment, ambient lighting, simple sensors. Schedule-based, no arbitration.
 FlexRay
Deterministic dual-channel bus, up to 10 Mbps. Time-triggered for safety-critical chassis (BMW active steering, Bosch ESP). High cost and complexity — CAN FD + Ethernet preferred in new designs.
Sensor / Actuator
Physical layer
PWM
Pulse Width Modulation. Analog-style control for motors, fans, throttle bodies. Duty cycle 0–100% maps to control position. Simple, robust, no protocol overhead.
 SPI / I²C
On-board sensor buses. SPI for high-speed IMU, ADC, flash memory. I²C for temperature sensors, EEPROMs, address-based multi-device. Typical distances: cm to meters within ECU or harness segment.
 SENT (SAE J2716)
Single-Edge Nibble Transmission. Unidirectional, single-wire, 4-bit nibbles. Throttle position, pressure sensors, torque sensors. Where analog is too noisy and CAN is overkill.
 Analog / 0–5V
Direct voltage signals for simple sensors: O2 sensors, coolant temp, MAP sensor. Susceptible to noise — being replaced by SENT and digital buses in new designs.

SDV Key Concepts

Service-Oriented Architecture

Vehicle functions exposed as software services. Providers and consumers decouple via SOME/IP or DDS service contracts at runtime.

▾

Hardware-Software Decoupling

Apps run on standardized compute platforms. Feature changes no longer require new ECU hardware — just a software update via OTA.

▾
03 /

OTA Lifecycle

Full firmware update pipeline from cloud campaign management to on-vehicle flash — with safety gates, risk scoring, and rollback at every stage.

▾

What SOA means in automotive

Traditional automotive software used signal-based communication — a CAN frame with a known ID maps to a specific signal. SOA replaces this with service contracts: a provider declares what data it offers and how to request it; consumers discover and bind at runtime via SOME/IP-SD.

AUTOSAR Adaptive's ara::com abstracts SOME/IP behind a typed C++ API. Service versioning allows rolling updates in mixed-version fleets. Failed services restart independently without affecting other services.

Why it matters for SDV

  • New features subscribe to existing services without ECU hardware change
  • Service versioning supports rolling updates in mixed fleets
  • Microservice architecture: separate update cycles per service
  • Fault isolation: failed service restarts independently
  • Standard interface enables third-party app ecosystem on vehicle

The shift from hardware-defined to software-defined

In traditional architectures, every feature tied to specific hardware. Adaptive cruise control required its own ECU with dedicated MCU, CAN transceivers, and fixed flash. Changing the feature meant an 18–36 month hardware revision cycle.

In SDV, the Vehicle Computer is standardized compute (ARM Cortex-A / NVIDIA Orin). Features run as software containers or VMs. The OEM can add a feature or change a behavior via OTA — no hardware touch required.

Architectural requirements

  • POSIX-compliant OS on zone controllers and Vehicle Computers
  • Container runtime (Docker, Podman) or hypervisor (QNX, ACRN)
  • Hardware abstraction drivers for peripherals
  • Secure boot and code signing to prevent unauthorized software
  • Resource isolation: safety-critical and non-critical partitioned by VM
  • AUTOSAR Adaptive ARA provides the standardized runtime APIs

OTA lifecycle stages

An OTA campaign begins in the cloud: the OEM uploads a signed firmware package to the UPTANE Image Repository. The Director Repository builds a vehicle-specific update manifest — which ECUs, which package versions, in what dependency order.

The vehicle OTA client fetches the manifest, validates UPTANE metadata signatures, checks eligibility (parked, battery SOC, connectivity), downloads and verifies the package hash, applies it, and reports success or failure back to the cloud.

Safety gates in my P3 implementation

  • 7-condition eligibility check before any ECU enters update mode
  • XGBoost risk score per vehicle: 12 features including connectivity stability
  • Dependency graph: gateway updates before perception before planning
  • Staged rollout: 1% canary → 10% → 50% → 100% fleet
  • Failure threshold triggers automatic campaign pause
  • Dependency-aware rollback: ML model predicts rollback success first
  • 9 failure mode simulations: battery death, timeout, corrupt package

Why the abstraction layer is critical

Without a VAL, every application must know the exact CAN ID, byte offset, and encoding of every signal it consumes. Add a new ECU or change a frame layout, and every consuming app breaks.

The VAL maps logical vehicle signals ("vehicle.speed_kmh", "hvac.cabin_temp_C") to physical CAN frames, SOME/IP events, or direct sensor readings. Apps consume the logical API and remain topology-agnostic — enabling hardware evolution without application rewrites.

Industry implementations

  • AUTOSAR Signal-Based / Service-Based Gateway routing
  • COVESA Vehicle Signal Specification (VSS) — open signal taxonomy
  • Eclipse Kuksa.VAL — open-source VAL server (gRPC / VISS API)
  • AUTOSAR Adaptive ara::com typed service interfaces
  • OEM-proprietary abstraction layers (NIO, Tesla, Rivian in-house)

Vehicle fleet as a software deployment target

In SDV, the software development cycle for a feature no longer ends at the factory. CI/CD pipelines build, test, sign, and deploy to a staging fleet before wider rollout. Feature flags allow dark launching: code ships to all vehicles, feature is off. The OEM enables it for a cohort, measures behavioral telemetry, and widens if KPIs are met.

What this requires

  • Signed software packages with UPTANE key hierarchy
  • Vehicle connectivity: 4G/5G always-on connection
  • Fleet management backend: campaign targeting, rollout control
  • Behavioral telemetry: did the new feature work correctly?
  • Rollback infrastructure: automatic recovery from failed updates
  • ISO 26262: functional safety impact assessment for every OTA update

From reactive DTCs to predictive intelligence

Traditional diagnostics: check engine light appears, technician reads P0300 code, replaces part. The vehicle was already degraded for weeks before detection.

Predictive diagnostics continuously streams sensor telemetry to a cloud ML model. XGBoost predicts failure probability 30+ days out and triggers proactive maintenance scheduling before the failure occurs.

My P2 implementation

  • 17 sensor health parameters streamed via MQTT to TimescaleDB
  • Cross-sensor correlation: camera + LiDAR degrading together → power root cause
  • XGBoost: 30-day failure probability per component
  • Cox Proportional Hazard: remaining useful life with confidence intervals
  • Fleet action engine: restrict route, schedule calibration, or pull from service
  • UDS diagnostic server exposes AI predictions over standard DoIP interface

AUTOSAR Classic vs Adaptive

AUTOSAR Classic

CP · R4.x · OSEK/VDX RTOS
OSOSEK/VDX RTOS. Cooperative + preemptive tasks. Fixed memory, no virtual addressing.
LanguageC only. ARXML-defined SWC interfaces. Autocode generation via TargetLink / MATLAB.
CommsCOM stack, PDU Router, CanTp. Signal-based, compile-time topology.
DiagnosticsDCM module. UDS over CanTp. DEM for DTC storage. Fim for function inhibition.
OTAFls / NvM modules. UDS 0x34–0x36 flash sequence. Separate bootloader required.
TargetsBody ECUs, powertrain, chassis, sensors. NXP S32K, Renesas RH850, Infineon TC3xx.
SafetyISO 26262 up to ASIL D. Static memory allocation aids safety analysis. No dynamic linking.

AUTOSAR Adaptive

AP · R21-11+ · POSIX PSE51
OSPOSIX PSE51 profile. Dynamic processes, virtual memory, MMU protection. QNX, Linux.
LanguageC++14/17. ara:: namespace APIs. Service-Oriented Architecture native support.
Commsara::com — SOME/IP and DDS binding. Runtime service discovery. Dynamic subscriptions.
Diagnosticsara::diag. UDS over DoIP natively. Remote diagnostic sessions. Dynamic DTC registration.
OTAara::ucm (Update and Config Management). UCM Master coordinates multi-ECU campaign.
TargetsDomain/zone controllers, Vehicle Computers. NVIDIA Orin, NXP S32G, Qualcomm SA8xxx.
SafetyISO 26262 up to ASIL B mixed criticality. Higher-ASIL functions partitioned by hypervisor.
→ Real-world deployment: In domain-based architectures (my NIO work), the gateway ECU ran AUTOSAR Classic for routing and signal processing, while the domain controller above it ran AUTOSAR Adaptive for SOME/IP service registry, OTA management, and fleet telemetry uplink. Both stacks coexist, communicating via PDU Router → Ethernet adapter → ara::com SOME/IP binding.
